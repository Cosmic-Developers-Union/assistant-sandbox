# VM 类型、客体 ISA 与部署后端(A02)

状态:已采纳(2026-10-24)。取代本决策须新增 ADR 并同步 TODO.md 的 S 组适用性与
阶段 1 出口条件。

## 决策

1. **VM 类型:Linux ABI 虚拟机(用户态)**。VM 直接实现 Linux 应用 ABI
   (系统调用、进程/线程/信号/文件语义),不启动原版 Linux 内核。
   据此 **S 组(S01–S19)整组判定为不适用**;G 至 O 组的全部验收仍为必做,
   由本 VM 的语义实现直接满足(而非由客体内核承担)。
2. **客体 ISA:RISC-V 64 位小端,RV64GC(RV64IMAFDC)+ Zicsr/Zifencei 用户子集**,
   与 [executor/cpu/riscv64](../../executor/cpu/riscv64/core.go) 现状一致;
   ELF 装载接受 soft/single/double 三种浮点 ABI。
3. **Linux ABI:asm-generic(riscv64)系统调用编号、数据结构布局与 errno 值**,
   以 glibc/musl 实际可链接执行为目标(见兼容配置 A03)。
4. **宿主平台:linux/amd64 与 linux/arm64(Go 原生编译)**。解释器为纯 Go,
   无宿主 ISA 假设;其他平台的采纳以 U10 部署矩阵实测为准。
5. **WASI 的角色:部署载体与开发基线,不是能力缩减依据**。现有 WASI 客体
   (assistant-bash.wasm)与 wazero 执行路径保留为兼容入口;本文按 TODO
   「目标与边界」的约束,WASI 不用于缩减 Linux、线程、后台进程或运行时需求。
   新能力一律先落在 Linux ABI 路径。
6. **执行后端:顺序解释器为语义基准后端**。允许未来增加翻译/缓存后端,
   但一切验收与差分以解释器语义为准,翻译后端不改变可观察语义。

## 依据

- 目标(TODO「目标与边界」)要求交付「提供基础 Linux 运行环境,在客体内部
  运行真实 CPython、Node.js 及其依赖」,并明确「以当前 CPU / ELF / Linux ABI
  实现作为任务拆解起点」。该目标是本决策的确认来源:验收对象是客体内运行的
  真实程序行为,不要求客体运行原版 Linux 内核。
- 已有资产:RV64 解释器(整数/乘除/AMO/LR-SC/压缩指令/单双精度浮点/CSR)、
  静态 ELF 装载、48 个已登记系统调用(含 fork、信号投递、等待、文件矩阵)、
  memfs/overlay/mountfs 存储栈、进程与资源计量。Linux ABI 路线是对已审计
  架构的延续,而非以实现局限倒推架构。
- 全系统路线(S 组 19 项:特权级、MMU、SBI 固件、设备树、块设备、内核启动)
  引入整套硬件仿真面,但不改变「CPython/Node 可在客体运行」这一验收结果;
  其 Linux 语义只是从本 VM 移交给客体内核,黑盒验收(G–O)完全相同。
  在目标未要求原版内核的前提下,双线并行或切全系统均属无收益的重复实现。

## 后果与义务

- **正确性门禁转移**:不启动原版内核意味着内核行为正确性由 A09 差分执行器
  (参考 Linux 对拍)与 G–O 各任务的行为断言承担;A10 追踪清单必须记录
  每项能力由本 VM 哪一层提供。
- **动态程序支持**:F 组(PT_INTERP、共享库、TLS)与 K 组(线程/futex)
  成为 CPython/Node 的硬前置,不可绕过。
- **旧 WASI 双轨期**:executor/wasm 与 executor/elf 并存直至 R06 收敛;
  收敛前新功能不得加在 WASI 路径上。
- 若未来目标变更要求启动原版 Linux 内核,须以新 ADR 推翻本决策、恢复 S 组
  必做地位,并重新评估 G–O 的实现归属(A10 同步)。
